MASSIVE ADS protocol: 1 vs 100 (Xbox 360, build v2.0.1149.0.02)

Introduction

This book documents the MASSIVE ADS protocol used by 1 vs 100 (Xbox 360, retail build v2.0.1149.0.02-2009-10-26, title 584A07D1). The game links the Massive Inc. client library (MassiveAdClient3, debug names XMassiveAdClient, CRequestManager, CMassiveAdObject, …) and drives it from Lua through a small Massive class.

The goal is a complete description of what the game sends and receives, and what it does with the answers: the wire format, the cryptography, the record layouts, the state machine and the Lua-side ad logic.

Confidence

Every statement is tagged:

  • [C] confirmed: read directly from the disassembly, the Lua source, or a string in the binary.
  • [I] inferred: strongly indicated by control flow or naming, not fully traced.
  • [U] unknown: identified but not decoded. These are collected in Status.

Limits

  • No live capture is available and the servers are not reachable from this environment. Wire-format statements are static. The reference code in Appendix C is internally consistent (it round-trips its own messages) but has not been checked against a real client or server. The field server massived exists to close that gap; Status lists what it is expected to answer.
  • The server endpoint (host and port) is provided by the game’s XLSP lookup on the tag MASSIVE. That path is treated as solved and is not re-derived here.

Process

  1. Anchor on strings. The Massive library carries debug strings (XMassiveAdClient::EnterZone, CRequestManager::SubmitRequest, /adsrv/5/enterZone, Adclient Massive Inc./, …). Every function that references one was identified and named after it.
  2. Walk the library call graph breadth-first from the request creators, response parsers and transport. This produced a closure of 322 functions in 0x824F0000–0x82510000, dumped one file per function under work/asm2/.
  3. Read the request builders bottom-up. Each Create*Request allocates a CRequestObject, the Write*Body function fills it, and sub_824FA478 seals it. Primitive writers (tag, u16, u32, u64, length-prefixed string, prepend vs. append) were decoded first and then used to read every body.
  4. Read the response parsers the same way, starting with the status byte and section tags, then the sub-tag dispatch tables (ReadAssetBlock uses a byte jump table at 0x82084998).
  5. Trace the value sources with cross-references to the globals (qword_82A0EEA8, qword_82A0EEB0, dword_82A0EF08, dword_82A0EF04, client fields +0x158/+0x15C).
  6. Rename in the IDB. All identified functions were renamed (massive_*, lua_Massive_*) and the database was saved. The rename table is work/ida/renames.py. Helpers are in work/ida/helpers.py.
  7. Verify by reconstruction. The framing, HMAC and body builders were written in Python (work/massive_envelope.py) and round-trip tested, which checks the framing is self-consistent.
  8. Carry names over from the debug build. A FLIRT signature built from the v1.0.808.0 database (rev3/tools/ida-1vs100-retail/signatures/1vs100-808-debug.sig) and a function matcher (code hash, string references, call graph, link order, opcode n-grams; result in 808-to-1149-matches.json) named 8 300 further functions in the retail database. Matcher names carry a function comment with the debug build address and the match method. Existing massive_* names were kept.
  9. Check against the capture. The debug client logs every field it writes and reads, and dumps each request. The dumps were decoded with the tag tables of this book and with massive-proto.

Conventions

  • Addresses are XEX virtual addresses (0x82xxxxxx). sub_XXXXXXXX is the IDA default name; massive_* names are the ones given during this work.
  • Big-endian is used everywhere (PowerPC). All multi-byte integers on the wire are big-endian.
  • [C], [I], [U] as defined in the Introduction.

Request objects

Every request is a CRequestObject subclass with a vtable of four entries [C]:

The object stores the request type code in its base constructor (sub_824F9030). The codes are listed in Requests. The buffer fields used by the append and prepend primitives are +0x1C (data pointer), +0x20 (cursor), +0x24 (length), +0x28 (capacity). The expected 20-byte digest is at +0x30.

Threads

MassiveThread (0x82501430) runs the network loop. Lua-facing calls such as EnterZone queue work or set desired state. Lua reads the outcome later through IsInZone, IsConnected and GetState.

Naming

Functions are renamed in the IDB with two prefixes: massive_ for the library and lua_Massive_ for the Lua binding. The full mapping with addresses is in Appendix A.

Staggered start

InitMassiveAndEnterLobbyZone (ads.lua:91) spreads the calls out so that thousands of consoles do not hit the servers together:

  • gameStartTime is the round-start cutoff (PTTimingsTable.RoundStartTable.roleCutoffTime) plus program start, for primetime (or the EP equivalent).
  • Late joiners (GetAbsoluteTime() > gameStartTime - 30) move their start to now + 30.
  • The total window is split in half: one half for Initialize, one half for EnterZone. Each call waits random(0, half × 8) / 8 seconds (1/8 s granularity).
  • The initial zone is introVideoAdZoneIndex = 1. For EP, STATE_ExtendedPlay.PredictQuestions picks the zone instead.

Impression and statistics rules are in Impressions and reporting. Statistics use GetState() and build a bitmap of which slots have content. How a and b are set [C]

XMassiveAdClient::Initialize (0x824F3178) takes an init structure. Its first two words are the SKU name pointer and the version pointer. sub_824F2368 (“XMassiveAdClient Player IDs”) stores them at +0x158 and +0x15C. A NULL structure is rejected with error 0x69 (Invalid initialization structure). An already initialized client is rejected with error 0xC9 (AdClient is already initialized).

For the shipped game this gives a = "mgs_1_vs_100_x360" and b = "edge".

How token33 is built [C]

  1. sub_824FC9F8 reads the console’s 6-byte hardware (Ethernet) address via sub_8246AC90 and formats it as uppercase hex with colons: AA:BB:CC:DD:EE:FF (17 characters).
  2. sub_82501EF8 (massive_EncodeToken) computes MD5(text).
  3. The 16-byte digest is printed as lowercase hex with %08x%08x%08x%08x into a 33-byte buffer: 32 characters and a NUL.
  4. The string writer uses strnlen, so the wire carries the 32 characters without the NUL.
token = hex_lower(MD5("AA:BB:CC:DD:EE:FF"))     32 characters on the wire

The MAD 3.x write-up derives the same 1D value from the same MD5 of the hardware-address string, which is an independent confirmation. The token is only produced when the device-identity object exists (dword_82A0EF08 non-null, sub_824FC880). Without it, the optional 1D field is omitted [C].

The token is a device identifier, not a secret: anyone who knows the MAC can compute it.

  • The User-Agent is Adclient Massive Inc./ followed by the build string XDK Test QFE 1v1009328.3 (string at 0x82081B0C).
  • POST is used for every request except the asset download, which uses GET (selected when the request type is 0x54).

Socket layer [C]

CMassiveSocket (constructor 0x82506DD0) owns the connection. The strings Transfer-Encoding: chunked (0x82084C64) and Content-Length: (0x82084C48) show the response reader handles both fixed-length and chunked bodies. The response status line is parsed with %256s %d and %256s %d %256[ a-zA-Z0-9] (0x82084C58, 0x82084C80).

Transport security [I]

No TLS code was found in the transport path. The request is built as plain text and written to a socket. The transport therefore appears to be plaintext HTTP. This has not been confirmed on the wire.

Retry and transaction handling [U]

TransactionHTTP (0x825061F0) is the transaction object. Its timeout and retry constants were not identified.

Response reading

Response bodies are parsed by the response parsers described in Responses. The transport delivers the body as a byte buffer that the CRequestObject owns. The buffer is then parsed in place by removing consumed bytes from the front and the trailer.

Sealing steps [C]

The body is assembled in an append buffer first. The routine then does the following, in this order:

  1. Time (timeFlag): append 3B followed by sub_824FE140() as a u64.
  2. Sign (signFlag): append 1E.
  3. Length: prepend u32 BE L, where L = current length + 22 when signed, otherwise L = current length.
  4. Type: prepend the type byte.
  5. MAC (signed only): HMAC-SHA1(key, buffer) over the current buffer, which now holds type | L | body | [;time] | [1E]. Append 00 14 and the 20 MAC bytes.
  6. Start marker: prepend 05.

HMAC [C]

  • Function: sub_82505760 (massive_HMAC_SHA1). It is a standard RFC 2104 HMAC built on the XeCrypt SHA-1 (j_XeCryptShaInit, j_XeCryptShaUpdate). Keys longer than 64 bytes are hashed first. The inner pad is 0x36 and the outer pad is 0x5C.
  • Key: the 32-byte ASCII string "1"×32 (0x31 repeated). The literal is at 0x8299F640, in a read/write data segment. It is also written into the OpenSession body as field 44 (see Requests).
KEY = 31 31 31 … 31   (32 bytes)

In this build the key is the constant. Three code paths read the literal and none writes it, and the binary contains no MT19937 code. The MAD 3.x line instead derives a per-session key from the server time, and sends it in the same field (see Cross-check with MAD 3.x). The constant is not a secret in either case.

The v1.0.808.0 debug client does what the MAD 3.x line does. In its captured session, field 44 held the 30-character value a750f9ed743bced9553e4f3481545b, and all 91 signed requests verify with that value as the key and none with "1"×32 (see Captured session). A retail console session against massived (2026-10-25) confirmed the retail reading: field 44 was "1"×32 and every request MAC verified with the literal.

Time value [I]

The 64-bit time comes from sub_824FE140 (CMassiveTime::GetTime in the v1.0.808.0 debug build). It reads a per-client time base at +0xE0 and computes the value from sub_824FC880 and sub_824FC8E8.

In the v1.0.808.0 capture the value is Unix time in milliseconds: the ImpressionUpdate logged at 2009-04-13 05:41:45,302 carries 1239601305302, which is that instant. The client logs it as Server Time(Timestamp), which suggests the base is synchronized to the locate server time. The retail build behaves the same: in a session against massived its first sealed request carried the locate server time plus 8 ms [C].

Verification of received messages [C]

The version byte 05 is consumed first by sub_824FA0B8. Verification is done by sub_824F9300 (massive_VerifyHMAC):

  • It takes the whole remaining buffer (+0x1C to +0x24) and computes HMAC-SHA1 with the same key.
  • The expected digest is referenced from +0x30: that field holds a pointer to a 20-byte copy. sub_824FA108 creates the copy from the response’s own 1E signature field (u16 len + 20 bytes, through massive_ReadStrLen). sub_824FA108 then removes those bytes from the buffer, so the MAC covers everything except the 1E trailer.
  • Asset downloads use a different check: plain SHA-1 of the body against the 20-byte asset hash, not an HMAC (see Asset downloads).

Consequences:

  • Responses are signed the same way requests are. The 1E marker stays in the buffer, so it is covered.
  • The response MAC does not cover the leading version byte (it is consumed first). The same holds for requests, whose MAC starts at the type byte.

Body grammar

Bodies are a flat sequence of tag bytes followed by values. There are no nesting markers except explicit length prefixes.

Tags at or above 0xC8 are always followed by a u32 length. Every reader skips such a tag when it does not know it (sub_824F96C0), and fails on an unknown tag below 0xC8, whose value length it cannot know [C]. DD, DE, E3, E4, E5 and E6 follow this rule. Writers append to the body buffer unless noted. Some writers prepend (the flag argument of the primitive is non-zero), so the final order can differ from the code order.

Player blocks (massive_WritePlayerUpdateBlocks, 0x824FA218) [C]

Up to four slots are read from the client table at +0x90 (20-byte entries: u32 occupied flag, then 16 bytes of player id). The loop stops at the first empty slot. Each slot writes:

E4 | 00 00 00 15 | 57 'W' | <slot index u8> | 41 'A' | 00 10 | <16-byte player id>

0x15 = 21 covers the 21 bytes from W to the end of the id. The v1.0.808.0 client writes the constant 19 (0x13) here for the same 21 bytes, so its player blocks overrun their length by two bytes; the retail writer has the correct value.

Responses

Responses use the same envelope as requests. Each response parser starts the same way, and each one requires an exact number of known fields.

Framing [C]

05                    protocol version, checked and removed by sub_824FA0B8
type                  request type + 1 (table below)
u32 BE L              bytes that follow, the signature trailer included
<fields>
1E                    signature tag (kept in the buffer, covered by the MAC)
00 14                 MAC length
<20-byte MAC>         HMAC-SHA1(key "1"x32) over type | L | fields | 1E
  • sub_824FA0B8 reads one byte, removes it from the buffer and returns true only when it is 0x05 (addi r11,r11,-5; cntlzw). This is the same byte that starts every request. MAD 3.x uses 0x03 in both directions, so the byte is the protocol revision and matches the 5 in the paths.
  • The type byte must equal the value listed below. Any other value fails the parse.
  • The signature is read by sub_824FA108 when the loop meets tag 1E. It reads a u16 length and keeps a pointer to a copy of that many bytes in the expected-digest field (+0x30). It then removes the length and the MAC bytes from the buffer (sub_824F9B90), leaving the 1E byte in place, and the loop limit L is reduced by 22. The length value is not checked; the comparison always uses 20 bytes.
  • sub_824F9300 computes HMAC-SHA1 with the literal key over the remaining buffer and compares 20 bytes. The literal is used directly, so the key does not depend on the OpenSession field 44.
  • An unknown tag at or above 0xC8 is followed by a u32 length and skipped (sub_824F96C0). An unknown tag below 0xC8 fails the parse. A response therefore cannot carry a time field 3B unless the parser lists it.

Records: IE (MAO), orders, assets, impressions

Records are parsed out of the EnterZone response body. The IE (inventory element) records are the ad placements in a zone, the order records set the rules for showing them, and the asset records describe the media files to download.

Every record is a block: tag, u32 length, fields. Each reader loops over its fields, counts some of them, and fails when the count is not exact. Readers skip unknown tags at or above 0xC8 and fail on unknown tags below it.

Asset downloads

An asset is one downloadable media file (video, texture, audio or model). Asset records (DE) sit inside the order blocks of the EnterZone response, and each is downloaded with a plain HTTP GET.

Lifecycle of an asset [C]

  1. Parsed: massive_ReadAssetBlock validates the record, and massive_CreateAsset (0x824F7BD8) creates the CMassiveAsset (see Records).
  2. Bound: the Lua side binds the asset’s IE (BindIE, see Lua integration). Binding asks the library to download.
  3. Requested: CreateDownloadBinaryRequest (0x824F7E90) checks the expected length (descriptor +0x28, asset field 07; 0x25D when zero), the URL (descriptor +0x2C, field 0C; 0x25B when missing or empty) and the digest buffer (asset +0x6C, field 04; 0x25C when missing), then builds a type 0x54 request. The expected length and the 20-byte digest are passed to CreateRequestHash (0x82505538), which stores the length at request +0x48.
  4. Downloaded: RequestDownloadBinary (0x82505420) sends GET <url>. The response body is kept in the request buffer.
  5. Verified: the download parser (0x82505610) runs two checks, in this order:
    • size: the body length must equal +0x48;
    • digest: SHA-1 of the body (sub_825056E0, plain XeCrypt SHA-1) must equal the 20 bytes at +0x30.
  6. Completed: CMassiveAsset::HandleResponse (0x824F8208) stores the data, or reports Failed in Download / Failed to Download Asset.

What the check is, precisely [C]

  • The digest is a plain SHA-1 of the file, not an HMAC. sub_825056E0 calls XeCryptShaInit, XeCryptShaUpdate and the finalizer, with no 0x36 or 0x5C pads. The earlier notes stated HMAC; that was wrong for this path.
  • The stored value is 20 bytes. The check does memcmp-style byte comparison of the 20 bytes.
  • The size check runs first. A file of the wrong size fails before any hashing.

The MAD 3.x write-up describes the same two checks in 3.x, but there the digest is an MD5 hex string of the file (the write-up’s md5sum, 32 characters). Our build uses SHA-1 over 20 bytes. See Cross-check with MAD 3.x.

Failure

On mismatch the request reports Asset data failed validity hash (in the download error path). The game-side state then waits for the next ad break.

Buffer and memory [C]

  • The download buffer is a CMemoryBuffer. If it cannot be allocated, Allocation failed: CMemoryBuffer in CMassiveAsset::HandleResponse() is logged.
  • Downloads that do not fit in memory are dropped with Ignoring newly downloaded Massive content as it requires too much memory. The game-side check uses Available virtual and Available Physical (logged with Creating massive content of size %u).
  • Bandwidth is throttled by SetNetBandwidth, which sets XMassiveAdClient::SetMaxReceiveRate and SetMaxSendRate.

Cache [C]

Downloaded content is written by the file worker (CFileAsyncWorker) into the cache directory game:\Massive, with cache name massive-cache-0. Temporary files use the pattern %s\%s_%lu.TMP. Cache jobs are CCacheJobReadFile, CCacheJobWriteFile, CCacheJobDeleteFile, CCacheJobClearCache and CCacheJobCreateCache. Whether content survives between sessions is [I].

An impression is a record that an ad was shown to the player. Impressions are the revenue-relevant events, so both the Lua side and the native side guard them.

Obstruction [C, Lua]

MonitorAdObstruction_Task(videoLength) (ads.lua:1455) runs during each Massive ad. IsAdObstructed() reports whether the ad is covered by something (a dialog or menu). At the start of an ad GameVars.Ads.obstructionDuringAd is set from the current state. An obstruction that occurs during the ad marks it obstructed, and that ad’s impression is dropped.

Native batching [C]

ImpressionUpdate requests (type 0xD3) carry the batch:

  • CRequestImpressionUpdate (0x82502BD8) is created by CreateImpressionUpdateRequest (0x824F4548). It fails with 0x12D if the zone has no current MAO state.
  • sub_82502C50 prepends the session pair (final order +, *), then writes the impression records (E6, one per IE name) and the player blocks. Then sub_82503520 appends the counters 21 and 29 and seals the message.
  • The request is sent to /impsrv/5/activity.

XMassiveAdClient::FlushImpressions (0x824F1A28) forces a send. It refuses with Attempting to flush impressions before internal time has been reached when the minimum interval has not passed. Trying to update before internal time has been reached is the same rule for updates.

The interval comes from the timers set by the locate response (see Session lifecycle and timers).

Impression record contents [C]

Each record carries the IE name only:

E6 | u32 (3 + len) | 3D '=' | u16 len | name

The name is what the Lua side bound (Video15_1, Video30_2, Text_1, …). The server maps it to the advertiser’s record. Any further per-view detail is not carried in the record.

Counters 21 and 29 [I]

The two u16 counters written at the end of every impression body come from this+0x50 and this+0x52 of the request object. Their meaning is not decoded [U]. They are most likely the number of records in the batch and a second count (for example succeeded or total). All 88 ImpressionUpdates of the v1.0.808.0 capture carried no records and 0 in both counters, which is consistent with that reading but does not prove it.

Statistics report [C, Lua]

UpdateAdBreakStats (ads.lua:1839) builds a LuaErrors record named AdBreakStats, or LobbyFPP for the lobby sponsor. It contains:

  • Connected(bool), Zone(name), Enter(time), DLTime(seconds);
  • State(code)(text) Error(code)(text) from GetState();
  • a content bitmap T.1:1 T.2:0 … V30.1:1 … V15.6:0.

The bitmap is the state of each IE: T.<n> for the four static images, V30.<n> for the three 30 s videos and V15.<n> for the six 15 s videos.

Statistics request (0xDA) [C]

The periodic statistics request (see Requests) carries three u16 counters from the global block at dword_82A0EF04: cache look-ups (58), cache hits (59) and cache mismatches (5C). They are sent to /impsrv/5/stats.

Time base [I]

The 64-bit time in each sealed envelope comes from sub_824FE140 (see Envelope). It is independent of the timers above.

Error recovery [I]

  • A failed LocateService logs Failed to Locate Service: %d and the session attempt stops.
  • A failed OpenSession logs Open Session Failed: %d.
  • Failed requests are removed from the queue (RemoveRequest, 0x824FAA58) and logged.
  • Lua-side retries are described in Lua integration: initialization retries after a random 1 to 100 seconds, and zone entry is retried on the next ad break.

Manifest

The client reads a manifest named mani.fest from the cache area. The parser is massive_ManifestParse (0x82500960) with a second entry point 0x82500BB8.

What is established [C]

  • The file is read through a random-access reader. Helper sub_82505C60 reads size bytes at offset into a destination buffer, with bounds checks against the file size. Helper sub_82505948 creates the reader over a buffer with a given size.
  • The reader tracks a cursor at +0x0C and a total size at +0x14. Parsing begins by checking a version or format field at +0x50. A value of 2 is rejected by the first check.
  • The parser reads 4-byte values with sub_82505C60 and uses them as offsets and counts. It builds lists with sub_8250A7E0, sub_82505AC0 and sub_82505B58.
  • Parsing failures are reported through the client error logger.

What is not decoded [U]

The record layout inside the manifest, the field names, and the meaning of each count were not decoded. The likely purpose is an index of the cached files: names, sizes and validity values. This is inference from the string mani.fest next to the cache path and from the presence of assets in the cache. It has not been confirmed.

Relation to the protocol

The manifest is local. Nothing in the request or response grammar refers to it. It was therefore not needed to build or verify a message.

The HMAC key

The write-up’s MT19937 derivation makes the key a per-session value. Its MassivePRNG seeds the generator from the server time string and writes 32 hex characters into a buffer that starts as placeholder text. The write-up then notes that the buffer was “unpopulated” in the decompiler, which matches what we see in the 2009 build.

Our checks on the 2009 build:

  • The literal "1"×32 is at 0x8299F640. That address is in a segment with read and write permission (perm 6, data).
  • Three code references read the literal: massive_VerifyHMAC (0x824F931C), massive_SealEnvelope (0x824FA594) and massive_WriteOpenSessionBody (0x82501950). No code was found that writes it.
  • The binary does not contain the MT19937 multiplier 0x6C078965 built with lis, so no MT19937 code is present.

The v1.0.808.0 debug client of the same game uses a per-session key: its captured requests verify with the 30-character field 44 value, not with "1"×32 (see Captured session). A retail console session against massived confirmed the constant: the retail build sends "1"×32 in field 44 and signs with it.

Conclusion for this build: the key is the constant "1"×32. This is strong evidence, not proof. A pointer-based write that was not visible to the cross-reference search would not be seen. The reading of the 2009 build is therefore: constant key. The 3.x line uses the time-derived key, and the 2009 line appears to predate it or to use a fixed test key. That was the claim in this book’s earlier chapters, and it stays, with this qualification.

Asset validity

The write-up’s 3.2 download check compares the MD5 of the file, written as a 32-character hex string, with the asset’s AssetHash string. The 2009 build compares the plain SHA-1 of the body with 20 bytes stored from the asset record. This is a second, independent difference from 3.x. The earlier notes in this book said HMAC here, which was wrong. The disassembly of 0x825056E0 shows a plain SHA-1.

Security analysis

This chapter lists what the protocol protects and what it does not. It is written from the code paths above. No live traffic was tested.

Integrity [C]

MechanismWhat it protectsStrength
HMAC-SHA1 envelope MAC on requestsintegrity of sealed requestsnone against an attacker: the key is a public constant in this build
HMAC-SHA1 response MACintegrity of sealed responsessame key, same weakness
SHA-1 asset check (no key)integrity of downloaded filesaccidental corruption only; anyone who can serve the asset can also serve a matching hash

The key is the 32-byte string "1"×32. It appears in the binary at a fixed address and in every OpenSession body. Anyone who has the game can compute a valid MAC for any message. The MAD 3.x line uses a per-session key derived from the server time, which is a stronger design, but the key is still sent in the same field, so it is not secret from the server either.

Confidentiality [I]

No TLS was found in the transport (see Transport). Request bodies contain the SKU, the device token, the session id and the Massive player id, and they travel in cleartext if the transport is plain HTTP. The player id and session id are sufficient to act as the client on the same session.

Identity [C]

The device token is MD5("AA:BB:CC:DD:EE:FF") in lowercase hex (the MAD 3.x write-up derives the same 1D value) (see Session identity and setup). It is a fixed function of the console’s MAC address. It is not secret, not salted and not bound to the session. It identifies the console to the server.

Replay [I]

The 64-bit time in each sealed envelope is covered by the MAC. Nothing in the protocol describes a nonce or a checked time window on the client side, so the server would have to enforce replay protection. Whether it does was not tested.

Authority of the server [I]

The client accepts the server’s MAC as proof of the body, using the same public key. It does not authenticate the server. A host that can answer on the expected endpoint can send any response that carries a valid MAC, which any host can compute.

Build and debug leakage [C]

  • The build string XDK Test QFE 1v1009328.3 is present in every request (16 field and User-Agent). It identifies a test build of the console SDK.
  • Debug strings such as XMassiveAdClient::EnterZone, CRequestManager::SubmitRequest and Failed to … ship in the retail binary.
  • The Lua debug switches DEFAULT_MASSIVE_BW_OVERRIDE and DEFAULT_ENTERZONE_IMMEDIATE are referenced but undefined (inactive in retail).
  • IsNotRetailBuild() gates debug labels only.

Denial of service [I]

  • Initialization retries use random waits of 1 to 100 seconds.
  • Zone entry is staggered by a random window across the start of the game so that consoles do not connect at once.
  • The client throttles downloads with SetNetBandwidth (7 KB/s by default).

These are operational controls, not security controls.

Data collected [C]

Impressions carry the IE name. Statistics carry the zone, the download time, the content bitmap and the state codes. Impressions and statistics are sent to the server even when the request body is only partly known. Identifiers are the device token and the SKU.

Summary

Treat the envelope and asset MACs as checksums. Treat the device token as a stable identifier. Treat every message as readable and forgeable by anyone with the game binary.

Appendix C: Reference code

The maintained implementation is the Rust crate crates/massive-proto, with the field server crates/massived. The Python reference below is kept for comparison; the Rust tests check that both produce the same bytes.

The Python reference is in work/massive_envelope.py (included below). It implements the sealing, the body primitives, the request bodies, the response framing and the MAC checks. Running it executes a self-test:

$ python3 work/massive_envelope.py
massive_envelope self-test OK (framing is internally consistent; not validated against live traffic)

The self-test checks:

  • a sealed message of type 0xCB round-trips and its MAC verifies;
  • a tampered message fails the MAC;
  • LocateService round-trips unsealed;
  • the player block has the exact bytes from massive_WritePlayerUpdateBlocks;
  • the token derivation (MD5 hex of the MAC string);
  • heartbeat, statistics and impression messages round-trip;
  • a signed response parses and its MAC verifies, and a corrupted one does not.

The self-test does not prove the layout matches a real server.

#!/usr/bin/env python3
"""
Reference implementation of the MASSIVE ADS (MassiveAdClient3) wire envelope and
field primitives, transcribed from the retail XEX (1vs100 v2.0.1149.0.02, title 584A07D1).

Source functions (XEX addresses):
  sub_824FA478  seal/finish buffer  -> seal()          (type/time/sign framing)
  sub_82505760  HMAC-SHA1           -> hmac_sha1()
  sub_824F9EA8  tag byte writer     -> tag()
  sub_824F9F68  u64 writer          -> u64()
  sub_824FA640  u16-length string   -> str16()
  sub_824F9EE8  u16 writer          -> u16()
  sub_824FA218  player-block writer -> player_blocks()
  sub_82501818  OpenSession body    -> open_session_body()   (0xCB)
  sub_824FF310  PlayerUpdate body   -> player_update_body()  (0xD8)
  sub_82503798  EnterZone body      -> enter_zone_body()     (0xCD)
  sub_82503520  Impression body     -> impression_body()     (0xD3)
  sub_824FEAF8  LocateService body  -> locate_body()         (0xC9, unsealed)

The Rust crate crates/massive-proto supersedes this file. The framing below is confirmed against the code. It has NOT been validated
against live server traffic (the server is no longer reachable and no capture exists).
The self-test only checks internal consistency of the framing.

All integers are big-endian (PowerPC).
"""
import hmac
import hashlib
import struct

# Constant HMAC key (32 ASCII '1' characters), literal at XEX 0x82084xxx
# (also written as a body field, tag 'D', by sub_82501818).
MASSIVE_HMAC_KEY = b"1" * 32

# Envelope type bytes (first argument of sub_824FA478 at each call site)
TYPE_OPEN_SESSION = 0xCB
TYPE_LOCATE_SERVICE = 0xC9
TYPE_CLOSE_SESSION = 0xD1
TYPE_PLAYER_UPDATE = 0xD8
TYPE_ENTER_ZONE = 0xCD
TYPE_IMPRESSION = 0xD3
TYPE_IMPRESSION_UPDATE = 0xD3
TYPE_PLAYER_UPDATE_BLOCK = 0xE4     # block tag inside body (sub_824FA218)

CLIENT_VERSION_STRING = b"XDK Test QFE 1v1009328.3"   # build string in OpenSession body (tag 0x16)
USER_AGENT_PREFIX = b"Adclient Massive Inc./"          # User-Agent prefix (sub_82506308)


def hmac_sha1(key: bytes, msg: bytes) -> bytes:
    """HMAC-SHA1 (sub_82505760 implements standard RFC 2104 ipad/opad)."""
    return hmac.new(key, msg, hashlib.sha1).digest()


# ---- field primitives (append semantics) --------------------------------------------

def tag(t: int) -> bytes:
    return bytes([t & 0xFF])


def u16(v: int) -> bytes:
    return struct.pack(">H", v & 0xFFFF)


def u32(v: int) -> bytes:
    return struct.pack(">I", v & 0xFFFFFFFF)


def u64(v: int) -> bytes:
    return struct.pack(">Q", v & 0xFFFFFFFFFFFFFFFF)


def str16(s: bytes) -> bytes:
    """u16 BE length followed by raw bytes (sub_824FA640, max 2000 bytes)."""
    if len(s) > 2000:
        raise ValueError("string longer than 2000 bytes")
    return u16(len(s)) + s


# ---- sealing ------------------------------------------------------------------------

def seal(body: bytes, msg_type: int, with_time: bool, sign: bool,
         time8: bytes = b"\x00" * 8, key: bytes = MASSIVE_HMAC_KEY) -> bytes:
    """
    Transcription of sub_824FA478(this, type, timeFlag, signFlag).

    Resulting layout:
      05 | type | u32 L | body | [';' | time8] | [1E] | [00 14 | HMAC-SHA1(20)]
    where L = len(body) + (9 if with_time) + (1 if sign) + (22 if sign)  -- i.e. the
    number of bytes that follow the L field.  HMAC covers  type|L|body|[;time]|[1E].
    """
    buf = bytearray(body)
    if with_time:                       # append ';' + 8-byte time
        buf += b";" + time8
    if sign:                            # append 0x1E marker
        buf += b"\x1e"
    length = len(buf) + (22 if sign else 0)
    buf = bytearray(u32(length)) + buf  # prepend L
    buf = bytearray(tag(msg_type)) + buf  # prepend type
    if sign:
        mac = hmac_sha1(key, bytes(buf))  # HMAC over type|L|body|;time|1E
        buf += u16(20) + mac              # append 00 14 + digest
    buf = b"\x05" + bytes(buf)          # prepend 0x05 (message start marker)
    return bytes(buf)


def unseal(msg: bytes, key: bytes = MASSIVE_HMAC_KEY, expect_time: bool = True,
           expect_sign: bool = True):
    """
    Inverse of seal(); returns (type, body, time8, mac_ok).
    L counts every byte after the L field, including the signature trailer
    (00 14 + 20-byte MAC) when signed.
    """
    if msg[0:1] != b"\x05":
        raise ValueError("missing 0x05 start marker")
    msg_type = msg[1]
    length = struct.unpack(">I", msg[2:6])[0]
    if len(msg) < 6 + length:
        raise ValueError("truncated: L=%d have=%d" % (length, len(msg) - 6))
    inner = msg[6:6 + length]          # body | [;time] | [1E] | [0014 | MAC]
    mac_ok = None
    if expect_sign:
        if len(inner) < 22 + 1:
            raise ValueError("signed message too short")
        trailer = inner[-22:]
        mac = trailer[2:]
        covered = msg[1:6 + length - 22]   # type|L|body|;time|1E  (HMAC input)
        mac_ok = (trailer[:2] == u16(20)) and hmac_sha1(key, covered) == mac
        inner = inner[:-22]
        if inner[-1:] != b"\x1e":
            raise ValueError("missing 0x1E sign marker")
        inner = inner[:-1]
    time8 = None
    body = inner
    if expect_time:
        if len(inner) < 9 or inner[-9:-8] != b";":
            raise ValueError("missing ';' time marker")
        time8 = inner[-8:]
        body = inner[:-9]
    return msg_type, body, time8, mac_ok


# ---- body builders -------------------------------------------------------------------

def player_blocks(players):
    """
    sub_824FA218 WritePlayerUpdateBlocks.  `players` is a list of up to 4 16-byte IDs.
    Each occupied slot i writes:
      E4 | 00 00 00 15 | 'W'(57) | i | 'A'(41) | 00 10 | <16-byte id>
    The loop stops at the first empty slot.
    """
    out = b""
    for i, pid in enumerate(players[:4]):
        if pid is None:
            break
        if len(pid) != 16:
            raise ValueError("player id must be 16 bytes")
        out += tag(0xE4) + u32(0x15) + b"W" + tag(i) + b"A" + u16(0x10) + pid
    return out


def open_session_body(a: bytes, b: bytes, token: bytes, players=(), flag_token=True):
    """
    sub_82501818.  Field order (append):
      '='(3D) str16(a) '>'(3E) str16(b) '<'(3C) 01 | 18 00 | 1B 01 |
      'D'(44) str16('1'*32) | [1D str16(token)] | 16 str16(build) | player blocks
    Sealed with type 0xCB, time=1, sign=1.
    `a`/`b` are the SKU name and version; `token` is device_token().
    """
    body = b"="
    body += str16(a) + b">" + str16(b)
    body += b"<" + b"\x01" + b"\x18" + b"\x00" + b"\x1b" + b"\x01"
    body += b"D" + str16(MASSIVE_HMAC_KEY)
    if flag_token and token:
        body += b"\x1d" + str16(token)
    body += b"\x16" + str16(CLIENT_VERSION_STRING)
    body += player_blocks(list(players))
    return seal(body, TYPE_OPEN_SESSION, with_time=True, sign=True)


def player_update_body(session_id: int, session_token: int, players=()):
    """
    sub_824FF310.  Prepends are used, so the final order is:
      '*'(2A) u64(session_token) '+'(2B) u64(session_id) | player blocks
    where session_token = qword_82A0EEB0 and session_id = qword_82A0EEA8 (globals).
    Sealed with type 0xD8, time=1, sign=1.
    """
    body = b"\x2a" + u64(session_token) + b"\x2b" + u64(session_id) + player_blocks(list(players))
    return seal(body, TYPE_PLAYER_UPDATE, with_time=True, sign=True)


def enter_zone_body(zone_name: bytes, session_id: int, session_token: int, players=(),
                    peer_public=None, peer_private=None, peer_port=None):
    """
    sub_82503798.  Appended order:
      'G'(47) str16(zone) '*'(2A) u64(token) '+'(2B) u64(session) | player blocks
      [10 u32 (sub_824F9F28)] [11 u32] [12 u16 (sub_824F9EE8)]  (all three or none)
    Sealed with type 0xCD, time=1, sign=1.
    """
    body = b"G" + str16(zone_name) + b"\x2a" + u64(session_token) + b"\x2b" + u64(session_id)
    body += player_blocks(list(players))
    if peer_public and peer_private and peer_port:
        body += b"\x10" + u32(peer_public) + b"\x11" + u32(peer_private) + b"\x12" + u16(peer_port)
    return seal(body, TYPE_ENTER_ZONE, with_time=True, sign=True)


def impression_body(field_0x50: int, field_0x52: int):
    """
    sub_82503520.  '!'(21) u16(field_0x50) ')'(29) u16(field_0x52).
    Per-impression records are appended by sub_82502C50 (not traced in detail).
    Sealed with type 0xD3, time=1, sign=1.
    """
    body = b"!" + u16(field_0x50) + b")" + u16(field_0x52)
    return seal(body, TYPE_IMPRESSION, with_time=True, sign=True)


def locate_body(a: bytes, b: bytes, token: bytes):
    """
    sub_824FEAF8 (LocateService).  '='(3D) str16(a) '>'(3E) str16(b)
    [1D str16(token) when the device-id source is present], unsealed (no time, no signature), type 0xC9.
    """
    body = b"=" + str16(a) + b">" + str16(b) + b"\x1d" + str16(token)   # no '<' tag in this writer
    return seal(body, TYPE_LOCATE_SERVICE, with_time=False, sign=False)


# ---- HTTP framing (sub_825061f0 / sub_82506308) ------------------------------------

def http_request(method: str, path: str, host: str, body: bytes, user_agent_suffix: bytes = b"XDK Test QFE 1v1009328.3") -> bytes:
    """
    Reproduces the request template:
      'POST ' <path> ' HTTP/1.1\\r\\nHost:%s\\r\\nContent-Length:%d\\r\\n'
      'Content-Type:application/massive\\r\\nUser-Agent:%s%s\\r\\n\\r\\n' <body>
    GET (asset download) uses 'GET ' with the asset URL (sub_82506308 checks request type 0x54).
    """
    head = (
        f"{method} {path} HTTP/1.1\r\n"
        f"Host:{host}\r\n"
        f"Content-Length:{len(body)}\r\n"
        f"Content-Type:application/massive\r\n"
        f"User-Agent:{USER_AGENT_PREFIX.decode()}{user_agent_suffix.decode()}\r\n\r\n"
    ).encode("latin-1")
    return head + body


# ---- session identity (sub_824FC9F8 / sub_82501EF8) -------------------------------

def console_mac_string(mac: bytes) -> bytes:
    """sub_824FC9F8: 6-byte MAC -> '%02X:%02X:%02X:%02X:%02X:%02X' (17 chars + NUL in an 18-byte buffer)."""
    if len(mac) != 6:
        raise ValueError("MAC must be 6 bytes")
    return ":".join("%02X" % b for b in mac).encode("ascii")


def device_token(mac: bytes) -> bytes:
    """sub_824F3A90 + sub_82501EF8: lowercase hex of MD5(mac string). The 33-byte buffer
    holds a NUL, but sub_824FA640 writes strnlen() bytes, so 32 characters go on the wire."""
    return hashlib.md5(console_mac_string(mac)).hexdigest().encode("ascii")


# ---- additional request bodies -----------------------------------------------------

def heartbeat_body(session_id: int, session_token: int):
    """sub_825074E0 (sealed type 0xD6, time+sign). Prepend-built: 2A QB0 2B QA8."""
    body = b"\x2a" + u64(session_token) + b"\x2b" + u64(session_id)
    return seal(body, 0xD6, with_time=True, sign=True)


def stats_body(session_id: int, session_token: int, c_x: int, c_y: int, c_z: int):
    """sub_82507800 (sealed type 0xDA, time+sign). Append-built:
    2B QA8 2A QB0 'X' u16 'Y' u16 '\\' u16 (counters from global struct dword_82A0EF04 +0x60/+0x62/+0x64).
    Field meaning of the three counters is not known [U]."""
    body = b"\x2b" + u64(session_id) + b"\x2a" + u64(session_token)
    body += b"X" + u16(c_x) + b"Y" + u16(c_y) + b"\\" + u16(c_z)
    return seal(body, 0xDA, with_time=True, sign=True)


def impression_record(ie_name: bytes) -> bytes:
    """sub_824FA6F0: E6 | u32 (len+3) | '=' | str16(name)."""
    inner = b"=" + str16(ie_name)
    return b"\xe6" + u32(len(inner)) + inner


def impression_request(session_id: int, session_token: int, names, players=(), count_0x50=None, count_0x52=None):
    """sub_82502C50 (records + player blocks) followed by sub_82503520 ('!' u16, ')' u16), sealed 0xD3."""
    body = b"\x2a" + u64(session_token) + b"\x2b" + u64(session_id)
    for n in names:
        body += impression_record(n)
    body += player_blocks(list(players))
    body += b"!" + u16(count_0x50 or 0) + b")" + u16(count_0x52 or 0)
    return seal(body, TYPE_IMPRESSION, with_time=True, sign=True)


# ---- response framing (sub_824FA0B8 / sub_824FA108 / sub_824F9300) -----------------

def parse_response(resp: bytes, key: bytes = MASSIVE_HMAC_KEY):
    """
    Response framing as implemented by the parsers (sub_825016D8, sub_82504728, ...):
      05            protocol version, must be 0x05 (sub_824FA0B8 removes it before parsing)
      type          request type + 1 (CA, CC, CE, D2, D4, D7, D9, DB)
      u32 BE L      bytes that follow, including the 22-byte trailer when signed
      ...tags...
      1E u16(20) MAC  signature trailer; MAC = HMAC-SHA1 over everything before the 00 14 bytes
    Returns (section_tag, inner_bytes_after_L_without_trailer, mac_ok).
    """
    if resp[0] != 0x05:
        raise ValueError("version byte is not 0x05")
    sec = resp[1]
    length = struct.unpack(">I", resp[2:6])[0]
    inner = resp[6:6 + length]
    # signature trailer is the last 22 bytes of the counted region, preceded by 0x1E
    if len(inner) < 23 or inner[-23:-22] != b"\x1e":
        return sec, inner, None
    mac = inner[-20:]
    covered = resp[1:6 + length - 22]        # type | L | ... | 1E  (version byte excluded)
    mac_ok = hmac_sha1(key, covered) == mac and inner[-22:-20] == u16(20)
    return sec, inner[:-22], mac_ok


# ---- self test ----------------------------------------------------------------------

def _selftest():
    time8 = bytes(range(1, 9))
    body = b"hello-massive"
    # signed + timed round trip
    msg = seal(body, TYPE_OPEN_SESSION, with_time=True, sign=True, time8=time8)
    t, b, tm, mac_ok = unseal(msg)
    assert t == TYPE_OPEN_SESSION, t
    assert b == body, b
    assert tm == time8, tm
    assert mac_ok is True, "HMAC did not verify"
    # unsigned, untimed (locate) round trip
    msg2 = seal(b"locate", TYPE_LOCATE_SERVICE, with_time=False, sign=False)
    assert msg2[0] == 0x05 and msg2[1] == TYPE_LOCATE_SERVICE
    assert struct.unpack(">I", msg2[2:6])[0] == len(b"locate")
    assert msg2[6:] == b"locate"
    # tampering must break the MAC
    bad = bytearray(msg); bad[10] ^= 0xFF
    assert unseal(bytes(bad))[3] is False
    # player block layout
    pb = player_blocks([b"A" * 16])
    assert pb == b"\xe4\x00\x00\x00\x15W\x00A\x00\x10" + b"A" * 16, pb.hex()
    # identity token: MD5 hex of MAC string, no NUL on the wire
    assert device_token(bytes.fromhex("001122aabbcc")) == hashlib.md5(b"00:11:22:AA:BB:CC").hexdigest().encode()
    hb = heartbeat_body(1, 2)
    assert unseal(hb)[0] == 0xD6 and unseal(hb)[3] is True
    st = stats_body(1, 2, 3, 4, 5)
    assert unseal(st)[0] == 0xDA and unseal(st)[3] is True
    ir = impression_request(1, 2, [b"Video15_1"])
    assert unseal(ir)[0] == TYPE_IMPRESSION and unseal(ir)[3] is True
    # response round-trip: build a signed response (version 05, type CC, L, body, 1E 0014 MAC)
    inner_no_sig = b"\x47\x01\x02\x03"     # arbitrary tagged content
    L = len(inner_no_sig) + 1 + 22              # counts body | 1E | 0014 | MAC
    covered = b"\xcc" + u32(L) + inner_no_sig + b"\x1e"
    resp = b"\x05" + covered + u16(20) + hmac_sha1(MASSIVE_HMAC_KEY, covered)
    sec, payload, ok = parse_response(resp)
    assert sec == 0xCC and ok is True and payload == inner_no_sig + b"\x1e", (sec, payload, ok)
    bad = bytearray(resp); bad[8] ^= 1
    assert parse_response(bytes(bad))[2] is False
    print("massive_envelope self-test OK (framing is internally consistent; not validated against live traffic)")


if __name__ == "__main__":
    _selftest()
